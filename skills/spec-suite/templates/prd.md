# PRD Template — `<project-name>`

No implementation detail in this document. If you find yourself naming a library, database, or framework, that belongs in the tech spec instead.

## 1. Problem
What problem does this solve, in 2-3 sentences? Who has this problem?

## 2. Target user
Who is this for? One primary persona is enough — don't invent multiple personas for a personal side project.

## 3. Core value proposition
The one thing this product must do well. If the elevator pitch needs more than one sentence, the scope is probably too broad.

## 4. Key features (MVP scope)
List only what's needed for a usable first version. Mark anything else explicitly as "Post-MVP" so it doesn't creep into the tech spec.

- Feature 1 — one-line description of what the user can do
- Feature 2 — ...

## 5. Out of scope
Explicitly list what this version will NOT do. This is as important as section 4 — it's what keeps the tech spec from over-building.

## 6. Success criteria
How do you know this shipped a working v1? Keep it concrete and checkable (e.g. "a user can create, edit, and complete a task without a page reload"), not aspirational metrics.

## 7. Signature moment (optional but encouraged)
Is there one interaction or visual detail that should define how this product feels to use (like Farwell's "Fade Bar")? Naming it here means the design system stage has something concrete to design around, instead of defaulting to generic UI.
